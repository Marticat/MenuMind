# MenuMind

Финальная модель для защиты: [запуск, версия, вход/выход и измерения](experiments/lora-study/FINAL_MODEL.md). Локальное демо сохранённой Qwen + LoRA запускается отдельно от API-провайдера сайта.

Лендинг и студия описаний блюд: React 19 + TypeScript + Vite, Express 5 и SQLite. Аккаунты, профили, рецепты, теги, история генераций и API-ключи сохраняются на сервере.

Материалы EDA и Midterm по тегам: [experiments/tags-midterm](experiments/tags-midterm/README.md).
В комплекте выполненный notebook, обученная модель, двухстраничный отчёт и семь слайдов.

Учебный эксперимент с LoRA, подбором параметров и сравнением конфигураций: [experiments/lora-study](experiments/lora-study/README.md). Новые пары RU/KK синтетические; результаты не заменяют редакторскую оценку.

Проверка требований и оставшиеся ограничения: [docs/project-audit.txt](docs/project-audit.txt).
Генерации возвращают `descriptionTags` для каждого канала и `variantTags`: упоминания,
подтверждённые исходными тегами карточки, с фрагментом текста, длиной и признаком краткости.
Это серверное извлечение по словарю; LLM генерирует тексты. После ручной правки теги
пересчитываются. LinUCB `v2-tags` использует признаки каждого варианта; статистика старой
версии не смешивается с новой. Схема и ограничения: [integration.txt](experiments/tags-midterm/integration.txt).

## Запуск

Нужен Node.js 20.19+ (проверено на 20.20.2). Все команды выполняются из этой папки, где находятся `server/`, `frontend/` и корневой `package.json`.

```sh
npm ci
npm run dev
```

Сайт: http://127.0.0.1:5173. Swagger: http://127.0.0.1:3001/api/docs. OpenAPI JSON: http://127.0.0.1:3001/api/openapi.json.

Создайте аккаунт на лендинге. Новому пользователю добавляются 27 примеров техкарт: основные блюда, закуски, супы и десерты, включая четыре карточки на казахском. Их можно изменить или удалить. Цены и вес порций демонстрационные; состав и способ приготовления — примеры для генерации описаний, без производственной раскладки ингредиентов. Общего демо-аккаунта и предустановленного пароля нет. При следующем входе восстановятся профиль, рецепты и последняя редакция. Старые данные прототипа из localStorage не импортируются автоматически.

Без `.env` используется явно обозначенный режим `template`: сервер составляет варианты из переданных полей без обращения к нейросети. Он не переводит названия и ингредиенты; для примера на казахском введите исходные поля на казахском. LLM-провайдер получает требуемый язык через промпт.

## Подключение LLM

Если `.env` ещё нет, скопируйте `.env.example` в `.env` в корне. В PowerShell:

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
```

Для GPT-5.6 Luna из описания проекта настройте:

```dotenv
LLM_PROVIDER=openai-compatible
LLM_BASE_URL=https://api.openai.com/v1
LLM_API_KEY=your-provider-key
LLM_MODEL=gpt-5.6-luna
LLM_REASONING_EFFORT=none
LLM_TIMEOUT_MS=8500
```

Вставьте свой OpenAI API-ключ в `LLM_API_KEY` локального `.env`. [GPT-5.6 Luna](https://developers.openai.com/api/docs/models/gpt-5.6-luna) поддерживает Chat Completions и структурированные ответы; доступ к модели зависит от вашего API-проекта. В `.env.example` оставлен `LLM_PROVIDER=template`, чтобы запуск без ключа работал: для обращения к Luna измените его на `openai-compatible`. После изменения окружения перезапустите сервер.

Провайдер должен поддерживать `POST /chat/completions` и `response_format: {"type":"json_object"}`. Можно использовать совместимый локальный endpoint. Модель задаётся через `LLM_MODEL`, без изменения кода. Для коротких описаний Luna настроена с `LLM_REASONING_EFFORT=none`: это отключает дополнительные рассуждения и помогает уменьшить задержку ([документация](https://developers.openai.com/api/docs/guides/reasoning)). Параметр необязателен: оставьте пустым для провайдеров без поддержки `reasoning_effort`. Ключ провайдера читается только сервером; переменные `VITE_*` для секретов не используются.

Все четыре канала генерируются одним запросом. Промпт содержит текущую техкарту, настройки голоса и до двух образцов стиля, выбранных по совпадению слов. Образцы не являются источником ингредиентов. При перегенерации передаётся предыдущий текст; его повтор отклоняется. Лимит, непустой ответ, известные запрещённые формулировки и отсутствие эмодзи проверяются на сервере. JSON-режим реализован по [официальной документации OpenAI](https://developers.openai.com/api/docs/guides/structured-outputs).

Сетевой запрос ограничен 8,5 секунды по умолчанию. Ошибки провайдера возвращают 502/503, таймаут — 504. Подмена ошибки шаблонным текстом не выполняется. Живой вызов платной модели требует вашего ключа; автоматические проверки используют имитацию ответов провайдера. Полноту фактической проверки и качество перевода оценивает редактор: правило в промпте не гарантирует отсутствие всех галлюцинаций.

## Возможности

- `/#home`: адаптивный лендинг, пример RU/KK, переход к регистрации и API.
- `/#register`, `/#login`: регистрация, вход; выход и смена пароля доступны в профиле.
- `/#studio`: генерация и перегенерация для Яндекс Еды, Wolt, сайта и печати; русский/казахский; редактирование, копирование, JSON-экспорт, оценки.
- `/#library`: создание, поиск, редактирование и удаление рецептов. Обязательно только название. Ингредиенты, метод, цена и вес можно не указывать (0 обозначает неуказанное числовое значение).
- `/#channels`, `/#brand`: лимиты, тон, примеры текстов, сохранение настроек в базе.
- `/#profile`: ресторан, кухня, язык и тон по умолчанию, предпочтительные/нежелательные теги, подборка и API-ключи.
- `/#personalization`: профили гостей, персональные описания, просмотр вариантов и проверка цикла «показ → корзина → обучение» на отдельной тестовой модели.
- `/#history`: последние 50 генераций и ручные правки. При удалении блюда исторический результат остаётся доступен для выгрузки.
- `/#docs`: примеры работающего API и список методов из OpenAPI запущенного сервера.

Теги извлекаются словарными правилами на русском, казахском и английском. Каждый тег содержит найденный фрагмент и поле-источник. Аллергены определяются только по явно переданному списку ингредиентов, отмечаются `confirmed: false`; отсутствие тега не означает отсутствие аллергена. Диетические свойства автоматически не приписываются. Подборка рецептов владельца (`/recommendations`) использует прежнее ранжирование: +3 за предпочтительный тег, −6 за нежелательный, сумма оценок описаний блюда от −3 до +3. Персонализация описаний гостей использует отдельную обучаемую модель LinUCB, описанную ниже. Векторная база не требуется.

## Персонализация описаний: LinUCB

LLM готовит до трёх вариантов одного блюда: `concise` (кратко), `ingredients` (состав), `method` (приготовление). Вариант состава доступен только при указанных ингредиентах, приготовления — при указанном методе. Без LLM работают явно обозначенные шаблоны. Лимиты каналов, проверки известных неподтверждённых фактов и запрещённых формулировок применяются к каждому варианту; полная проверка фактов остаётся за редактором. Профили гостей не передаются LLM.

`POST /description-sets` подготавливает и кеширует варианты для рецепта, языка и настроек бренда. При подключённой LLM первая подготовка вызывает до трёх запросов провайдера параллельно; при частичной ошибке набор не сохраняется. Повторная подготовка использует кеш. Изменение техкарты, тона, лимитов, примеров, модели или провайдера делает предыдущий набор неактуальным. `POST /personalizations` использует только подготовленный актуальный набор и не обращается к LLM. Одинаковые тексты внутри выбранного канала объединяются в один вариант выбора.

Для каждого ресторана и режима (`live` / `demo`) сохраняется отдельный disjoint LinUCB. Контекст содержит предпочтение типа описания, язык, канал, теги интересов гостя, теги блюда, их пересечения и сглаженные результаты прошлых показов этому гостю по каждому типу описания. Вектор нормируется по L2; идентификатор гостя используется для поиска профиля и истории, а не как числовой признак. Профиль ресторана отделён от профилей гостей.

Алгоритм выбирает максимум `xᵀθ + α√(xᵀA⁻¹x)`, где `θ = A⁻¹b`, `α = 0.5`, начальные `A = I`, `b = 0`. Матрицы решаются через разложение Холецкого. При равных оценках используется явно заявленное предпочтение гостя, иначе случайный выбор среди равных вариантов. После наблюдения обновляется только выбранное действие: `A += xxᵀ`, `b += reward × x`. Контекст фиксируется в момент выбора; последующая смена профиля не меняет обучающий пример. Версия признаков и модели хранится вместе с решением. Основа: [Li et al., LinUCB](https://www.schapire.net/papers/www10.pdf).

### Контракт интеграции

Все маршруты имеют префикс `/api/v1` и используют серверный Bearer-ключ ресторана либо авторизованную cookie-сессию с CSRF для изменений. Ключ нельзя размещать в браузере гостя: запросы гостевого сайта проходят через ваш сервер, который определяет идентификатор гостя из своей сессии. Авторизация конечных гостей остаётся ответственностью интеграции.

| Метод                                    | Назначение                                                                                                                                                                                                 |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PUT /customers/{id}`                    | Создать или заменить профиль: `name`, `language` (`ru`/`kk`), `descriptionPreference` (`auto`/`concise`/`ingredients`/`method`), `preferredTags` (ID из `/tags`). ID: 1–80 латинских букв, цифр, `_`, `-`. |
| `GET /customers`, `GET /customers/{id}`  | Последние 200 профилей или один профиль внутри ресторана.                                                                                                                                                  |
| `POST /description-sets`                 | Подготовить варианты: `{recipeId, language}`. Возвращает `id`, `variants[{style,label,texts,limits}]`, `provider`, `requiresReview`.                                                                       |
| `POST /personalizations`                 | Выбрать: `{requestId, customerId, recipeId, channel?, mode?}`. `requestId` — UUID, `channel` по умолчанию `website`, `mode` — `live`. Язык берётся из профиля гостя.                                       |
| `POST /personalizations/{id}/impression` | Подтвердить фактический показ с телом `{}` в течение 10 минут после выбора.                                                                                                                                |
| `POST /personalizations/{id}/feedback`   | Сообщить `{event:"add_to_cart"}` после подтверждения показа и до истечения окна реакции.                                                                                                                   |
| `GET /personalization/stats`             | Количество решений, подтверждённых показов, закрытых наблюдений, добавлений и ожидающих реакций по типу описания и режиму.                                                                                 |

Пример последовательности запросов с серверной стороны интеграции:

```js
const base = 'http://127.0.0.1:3001/api/v1';
async function call(path, method, body) {
  const response = await fetch(base + path, {
    method,
    headers: {
      Authorization: `Bearer ${process.env.MENUMIND_API_KEY}`,
      'Content-Type': 'application/json',
    },
    body: JSON.stringify(body),
  });
  const result = await response.json();
  if (!response.ok) throw new Error(result.error.message);
  return result;
}

await call('/customers/guest-42', 'PUT', {
  name: 'Гость 42',
  language: 'ru',
  descriptionPreference: 'ingredients',
  preferredTags: ['mushrooms'],
});
await call('/description-sets', 'POST', {
  recipeId: 'RCP-8843-VEG',
  language: 'ru',
});
// Один requestId на логический запрос; при сетевом повторе сохраните его.
const requestId = crypto.randomUUID();
const selected = await call('/personalizations', 'POST', {
  requestId,
  customerId: 'guest-42',
  recipeId: 'RCP-8843-VEG',
  channel: 'website',
  mode: 'live',
});
// Передайте selected.text и selected.id гостевому интерфейсу.
// Только после фактического отображения:
await call(`/personalizations/${selected.id}/impression`, 'POST', {});
// Только при реальном добавлении этого блюда в корзину:
await call(`/personalizations/${selected.id}/feedback`, 'POST', {
  event: 'add_to_cart',
});
```

Выбор возвращает `id`, `text`, `style`, `label`, `customerId`, `recipeId`, `language`, `channel`, `mode`, `provider`, `requiresReview`, `modelVersion`, диагностические UCB-оценки (не вероятности), `observations`, `shownAt`, `feedbackDeadline`, `reward`. Повтор с тем же `requestId` и payload возвращает прежнее решение; другой payload получает 409. Для нового показа нужен новый `requestId`.

Окно реакции — 30 минут от подтверждения показа. Добавление в корзину даёт награду 1 сразу; подтверждённый показ без добавления к концу окна — 0. Истёкшие окна закрываются при следующем запросе выбора, обратной связи или статистики; отдельный фоновый процесс не нужен. Неподтверждённые показы не становятся отрицательными примерами. Повтор подтверждения не продлевает окно, повтор добавления не обучает модель дважды. Запоздалое добавление получает 409. Тело обратной связи не принимает произвольную награду или контекст.

Коды 409: `DESCRIPTIONS_REQUIRED` — подготовьте актуальные варианты; `SOURCE_CHANGED` — техкарта/настройки изменились; `IDEMPOTENCY_CONFLICT` — повтор requestId с другими полями; `DECISION_EXPIRED` — выбор не показан за 10 минут; `IMPRESSION_REQUIRED` — сначала подтвердите показ; `FEEDBACK_EXPIRED` — окно реакции завершено.

В интерфейсе `/#personalization` все решения идут в `demo`: можно создать двух гостей с разными предпочтениями, получить описания одного блюда, подтвердить тестовый показ и добавить блюдо в тестовую корзину. Рабочая модель `live` и её история не используют эти реакции. Оценки текстов в студии также не обучают LinUCB. Рост конверсии ещё не измерен: тесты проверяют механику обучения, а эффект на гостях требует реальных показов и сравнения с контрольной выдачей.

## API

Полная актуальная спецификация: `/api/openapi.json`, интерактивный клиент: `/api/docs`.

| Группа           | Методы                                                                                               |
| ---------------- | ---------------------------------------------------------------------------------------------------- |
| Аккаунт          | `POST /api/v1/auth/register`, `/auth/login`, `/auth/logout`; `GET /auth/me`; `PUT /account/password` |
| Пространство     | `GET /api/v1/workspace`, `/profile`; `PUT /profile`, `/settings`                                     |
| Рецепты          | `GET/POST /api/v1/recipes`; `GET/PUT/DELETE /recipes/{id}`                                           |
| Теги и подборка  | `GET /api/v1/tags`, `/recommendations`; `POST /tags/extract`                                         |
| Описания         | `GET/POST /api/v1/generations`; `GET/PATCH /generations/{id}`; `PUT /generations/{id}/feedback`      |
| Ключи            | `GET/POST /api/v1/api-keys`; `DELETE /api-keys/{id}`                                                 |
| Проверка сервиса | `GET /api/v1/health`                                                                                 |

Серверным интеграциям нужен `Authorization: Bearer <ключ из профиля>`. Этот ключ даёт доступ только к данным его владельца и не позволяет управлять другими ключами или паролем. Секрет показывается один раз, хранится только его SHA-256. Отозванный ключ немедленно перестаёт работать.

Браузер использует HttpOnly / SameSite=Lax cookie. Для изменений нужен `X-CSRF-Token`, возвращаемый при входе и через `/auth/me`. Origin проверяется относительно `APP_ORIGIN`; произвольный CORS не включён. Пароли хешируются scrypt с индивидуальной солью. Все запросы к пользовательским данным ограничены идентификатором авторизованного пользователя. Включены лимиты запросов и попыток входа. Смена пароля завершает остальные браузерные сессии; API-ключи отзываются отдельно.

```sh
curl http://127.0.0.1:3001/api/v1/generations \
  -H "Authorization: Bearer $MENUMIND_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: menu-item-42-v1" \
  -d '{"recipe":{"name":"Суп из тыквы","ingredients":["Тыква","Вода","Соль"]},"language":"ru","maxLength":250}'
```

Вместо `recipe` можно передать `recipeId` сохранённой карты. `previousId` задаёт предыдущую генерацию для перефразирования. Без него сервер находит последнюю генерацию этой карты или точно совпадающего нормализованного `recipe` в истории текущего пользователя. Для нового варианта используйте новый `Idempotency-Key` или не передавайте его. `Idempotency-Key` необязателен: тот же ключ и запрос в течение суток возвращают существующий результат; другой запрос с тем же ключом получает 409. Одновременный повтор получает 409, его можно повторить после завершения первого запроса. Идемпотентность сохраняется в SQLite.

## Хранение и запуск сборки

`DATABASE_PATH` по умолчанию — `./data/menumind.sqlite`; папка и миграции создаются автоматически. Таблицы: `users`, `profiles`, `sessions`, `api_keys`, `recipes`, `tags`, `recipe_tags`, `generations`, `idempotency`, `customers`, `description_sets`, `personalization_decisions`, `bandit_models`, `migrations`. Миграция 2 добавляет персонализацию, сохраняя существующие аккаунты и рецепты. Профили гостей, варианты, контексты показов, результаты и матрицы LinUCB переживают перезапуск. Связанные записи имеют внешние ключи; SQLite работает в WAL-режиме. База и `.env` исключены из Git.

```sh
npm run build
npm start
```

После сборки один Express-сервер отдаёт сайт и API на http://127.0.0.1:3001. Для этого режима укажите `APP_ORIGIN=http://127.0.0.1:3001` в `.env`. Для размещения за HTTPS укажите `NODE_ENV=production`, внешний HTTPS `APP_ORIGIN`, постоянный том базы и `HOST=0.0.0.0`. `TRUST_PROXY=1` включается только за одним доверенным reverse proxy. Production-cookie требует HTTPS. Эта версия рассчитана на один процесс API и локальный диск SQLite; несколько реплик требуют общего хранилища лимитов/блокировок и другой стратегии БД.

Резервную копию делайте через SQLite backup API либо после корректной остановки сервера (не копируйте только основной файл во время активного WAL). POS-интеграции, отправка в маркетплейсы, webhooks, восстановление пароля по email и подтверждение адреса не реализованы. Экспорт выдаёт JSON для передачи в вашу систему.

## Живая проверка LLM и эксперимент с промптами

**Дополнительный эксперимент по генерации RU/KK (версия 2; основной мидтерм с обученной моделью — в tags-midterm):** [Notebook](experiments/llm-v2/MenuMind_final.ipynb), [HTML](experiments/llm-v2/MenuMind_final.html), [отчёт PDF](experiments/llm-v2/MenuMind_report.pdf), [презентация](experiments/llm-v2/MenuMind_presentation.pptx), [инструкции](experiments/llm-v2/README.md). На новой итоговой выборке: 16/16 первичных подробных ответов и 16/16 изменённых перегенераций; среднее первичного запроса 2,14 с, около $0,256 за 1 000 запросов по публичному тарифу на 07.10.2026. Один неподтверждённый тип заведения отмечен для редактора; человеческая проверка RU/KK ещё не выполнена.

Генератор допускает одну корректирующую попытку при нарушении ограничений или повторе текста. Она разделяет исходный таймаут 8,5 секунды с первой попыткой. `usage` суммирует расход, `providerAttempts` хранит метаданные попыток; основной response ID относится к выданному ответу. Шаблоны не используются вместо ошибки LLM. Проверка фактов остаётся ограниченной словарными правилами.

**Предыдущая итерация, сохранённая для аудита:**

[Выполненный Notebook](experiments/llm/MenuMind_LLM_evaluation.ipynb), [HTML-отчёт](experiments/llm/MenuMind_LLM_evaluation.html) и [описание эксперимента](experiments/llm/README.md) включают 32 входных примера RU/KK, очистку, EDA, 8 графиков и разделение по блюдам на разработку и итоговую проверку. Анализ повторно выполняется без ключа: ответы и входы встроены в Notebook.

6 октября 2026 выполнено 80 настоящих вызовов настроенной модели, включая браузерную проверку пути «провайдер → API → текст карточки». Сохранены сырые ответы, время, токены и идентификаторы провайдера. На итоговой выборке сервер принял 16/16 ответов подробного промпта и 11/16 простого; это не оценка полной фактической точности. Зафиксированы неподтверждённые формулировки и 2 повторных ответа при 8 перегенерациях. Максимальное время в сравнении — 4,648 секунды; нагрузочный SLA не проверялся.

Новые профили получают лимит 250 символов для всех каналов; сохранённые лимиты ресторанов не переписываются. Успешная генерация сохраняет `usage`, `providerResponseId`, `providerRequestId` и `providerModel`; шаблонный режим возвращает для них `null`. Промпт поясняет выбранный тон, а ошибки соединения с моделью возвращаются как `LLM_UNAVAILABLE`.
