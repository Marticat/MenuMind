MenuMind: как используются теги описаний

Теги карточки и упоминания в тексте

Поле tags содержит найденные в карточке ингредиенты и способы приготовления.
Некоторые ингредиенты также отмечаются как возможные аллергены. Отсутствие
такого тега не позволяет сделать вывод о безопасности блюда.

У описания свой набор тегов. Например, при составе «курица, рис» фраза
«Блюдо в меню» не получает тегов упоминаний, а «Курица с рисом» получает
chicken и rice. Сервер ищет эти слова отдельно в тексте каждого канала
и сверяет найденные теги с исходной карточкой. После ручной правки
упоминания пересчитываются, чтобы в результате не оставались старые теги.

Структура descriptionTags.website (аналогично для yandex, wolt и print):

  version: description-tags-v1
  method: source-grounded-dictionary
  mentioned: [{id, label, kind, evidence, sourceEvidence, confirmed:false}]
  evidence: {field:"description", text:"фрагмент описания"}
  sourceEvidence: основание тега в исходной карточке
  short: длина текста не более 100 символов
  charLength: длина по JavaScript UTF-16, как в проверке лимитов API
  requestedStyle: concise / ingredients / method / null

Для дополнительного варианта текста используется variantTags с той же структурой.
requestedStyle хранит стиль, который был запрошен при генерации. Чтобы установить,
получился ли этот акцент в самом тексте, нужна отдельная оценка. Словарь покрывает
только заданные варианты слов и может пропускать синонимы. В текущей версии LLM
возвращает описания, а сервер рассчитывает теги после генерации.

Запросы API

POST /api/v1/generations
  Создаёт описания и возвращает tags, descriptionTags и variantTags.

PATCH /api/v1/generations/{id}
  Сохраняет ручную правку и заново рассчитывает упоминания.

POST /api/v1/description-sets
  Подготавливает варианты с тегами для каждого канала.

POST /api/v1/personalizations
  Выбирает описание и возвращает его теги и оценки LinUCB.

POST /api/v1/personalizations/{id}/impression
  Подтверждает, что выбранное описание показано гостю.

POST /api/v1/personalizations/{id}/feedback
  Принимает событие {"event":"add_to_cart"}.

Авторизация и CSRF описаны в основном README. Swagger доступен по /api/docs,
спецификация OpenAPI по /api/openapi.json. Для демонстрации сначала нужно
подготовить варианты и получить выбор, затем подтвердить тестовый показ
и добавить блюдо в тестовую корзину. Следующий выбор использует обновлённую историю.

Выбор описания

LinUCB v2-tags оценивает каждый вариант по его собственному вектору признаков.
В него входят предпочтения гостя, теги карточки, упоминания в тексте и их
совпадения с предпочтениями. Также учитываются язык, канал, длина описания
и история до текущего решения. В базе сохраняется вектор выбранного варианта
на момент выбора, поэтому последующие изменения профиля не меняют обучающий пример.

Итоговая оценка UCB складывается из оценки награды и бонуса за неопределённость.
Использовать её как вероятность покупки нельзя. Версия модели изменена на v2-tags,
поскольку добавились признаки. Она накапливает статистику отдельно от v1.
Старые отложенные реакции обрабатываются со своей версией и размером вектора;
кеш вариантов тоже имеет отдельную новую версию.

Учёт реакции

После подтверждённого показа открывается окно в 30 минут. Если гость добавляет
блюдо в корзину, модель получает награду 1. После истечения окна без добавления
награда равна 0. Неподтверждённый показ не создаёт отрицательный пример,
а повторное событие не обучает модель второй раз. Demo и live хранятся отдельно.
Данные эксперимента с английскими тегами не попадают в рабочую историю гостей.

Какие данные понадобятся для следующего эксперимента

Чтобы измерить результат персонализации, нужно связать выбранное описание,
его фактический показ и последующее действие. Для журнала предлагаются поля:

  decision_id, event_id, anonymous_customer_id, recipe_id, description_set_id,
  variant_id, model_version, features_snapshot, language, channel,
  selected_at, shown_at, feedback_deadline, added_at, finalized_reward, mode.

Для A/B-теста пользователей следует случайно распределить между контрольной
и персонализированной выдачей, сохраняя их группу при повторных посещениях.
Основной показатель: добавления в корзину на подтверждённый показ.
До запуска нужно выбрать окно наблюдения и способ расчёта доверительного
интервала с учётом повторных пользователей. Параллельно стоит учитывать
задержку, ошибки генерации и расхождения текста с исходными фактами.

К обсуждению на защите

Внешняя LLM соответствует техническому заданию, которое разрешает генерацию
через API. Обученная в Midterm модель решает задачу тегов. Для разреженных
TF-IDF-признаков логистическая регрессия даёт простой исходный результат,
с которым можно сравнивать дальнейшие подходы.

Categories используются как ответ при обучении. Если передать их модели
во входных признаках, оценка перестанет показывать способность восстановить
теги по тексту. Рейтинг рецепта тоже не подходит для оценки эффективности
описания: неизвестно, какой текст видел человек и повлиял ли он на оценку.

Модель только по названию оказалась лучше варианта с составом. Можно предположить,
что длинные списки ингредиентов добавляют шум в TF-IDF, но этот механизм ещё
не проверялся. По macro-F1 словарь тоже оказался сильнее полной модели:
выигрыш по общей метрике не означает улучшения каждого класса.

О влиянии на заказы пока судить нельзя. Для этого нужны реальные показы,
реакции гостей и контрольная выдача.
