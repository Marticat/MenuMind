# Проверка персонализации на тестовых данных

Реальных данных показов и заказов пока нет. Этот эксперимент демонстрирует обучение LinUCB на искусственных реакциях и **не подтверждает рост реальных заказов**. Добавление в корзину не считается покупкой.

## Результаты

Каждая ячейка — тестовые добавления / показы и их доля. Для каждого сценария выполнены три запуска по 300 показов, всего 900 показов на способ выбора.

| Сценарий                          | LinUCB            | Случайный вариант | Всегда краткое описание |
| --------------------------------- | ----------------- | ----------------- | ----------------------- |
| У гостей разные предпочтения      | 461 / 900 (51,2%) | 288 / 900 (32,0%) | 284 / 900 (31,6%)       |
| Стиль не влияет на реакцию        | 257 / 900 (28,6%) | 257 / 900 (28,6%) | 257 / 900 (28,6%)       |
| Все предпочитают краткое описание | 576 / 900 (64,0%) | 280 / 900 (31,1%) | 583 / 900 (64,8%)       |

Первый сценарий показывает, что алгоритм может использовать различия в предпочтениях. Второй служит проверкой отсутствия эффекта: один и тот же случайный исход применяется ко всем способам, поэтому результаты совпадают точно. Третий показывает цену исследования альтернатив: когда всем подходит один стиль, фиксированный вариант может быть лучше обучаемого. Эти цифры зависят от заданных условий симулятора; это не прогноз для ресторана и не оценка причинного эффекта.

## Как устроена проверка

- Используются настоящие `buildContext`, `chooseArm` и `updateModel` из приложения: версия `linucb-descriptions-v2-tags`, `alpha = 0.5`. В симуляции меняется только источник случайного выбора при равных оценках.
- Шесть вымышленных профилей, 12 блюд, три стиля: кратко, состав, приготовление. Профили выбирают стиль автоматически. Описания создаются локальными шаблонами без платных запросов.
- При разных предпочтениях подходящий стиль циклически назначен гостям. Вероятность реакции — 65% для подходящего стиля и 15% для остальных. В сценарии без эффекта — 30% для всех. Это предположения, а не измеренные вероятности.
- Начальные состояния генератора: `7`, `19`, `42`. Каждая модель начинает с нуля в каждом запуске и сценарии. Способы выбора получают одинаковую последовательность гостей, блюд и случайных условий реакции.
- Выбор делается до вычисления реакции. Алгоритм получает только результат выбранного действия; скрытые вероятности ему не передаются. Профили и история реакций доступны через обычные признаки приложения.
- Матрицы и история симуляции существуют только в памяти. База аккаунтов и рабочие либо интерактивные тестовые модели не читаются и не изменяются.
- Это короткая проверка механизма на шести профилях. Она не проверяет перенос на новых гостей, качество перевода, платную LLM или работу ресторана. Параметры не подбирались по этим исходам.

## Воспроизведение

Из корня проекта после установки зависимостей:

```sh
npm run study:personalization
npm test
```

`results.json` содержит все 2700 событий: профиль, блюдо, скрытые вероятности, случайное число, выбранные стили и результаты. `summary.json` содержит сводку и результаты каждого запуска; её показывает приложение. Версии и SHA-256 исходных файлов сохранены в обоих файлах (текст нормализован в UTF-8 LF). Тесты проверяют соответствие исходникам, исходам событий и итоговым счётчикам. После изменения симулятора или зависимых исходников нужно повторно создать отчёты.

## Демонстрация в приложении

1. Откройте **Персонализация → Добавить примеры блюд**. Для существующего аккаунта добавятся только отсутствующие примеры. Изменённые техкарты сохраняются; повторный импорт не создаёт дубликаты. Новые аккаунты получают их сразу.
2. Создайте профиль гостя, выберите блюдо и получите описание. Подтвердите тестовый показ, затем добавьте блюдо в тестовую корзину — реакция обновит отдельную тестовую модель.
3. Для казахского профиля выберите казахскую техкарту: шаблонный режим не переводит входные поля.
4. В блоке **Что показывает персонализация** переключите три сценария. Ниже отдельно показаны тестовые и рабочие события вашего аккаунта. Сводка симуляции фиксирована; ручные действия меняют только счётчики аккаунта и его тестовую модель.

Добавлены 6 русских и 6 казахских примеров: блюда с птицей и рыбой, чечевичные супы, омлеты, салаты с нутом и творожные десерты. Для каждого проверены все три шаблонных варианта и четыре канала с лимитом 250 символов. Цены и веса в новых карточках не заданы (0); это примеры для генерации, а не производственные рецептуры. Казахские тексты требуют редакторской проверки перед публикацией.

Новые авторизованные маршруты: `POST /api/v1/recipes/demo` с телом `{}` импортирует примеры; `GET /api/v1/personalization/study` возвращает сводку. Правила авторизации и CSRF совпадают с остальным API.

## Что нужно для проверки на реальных гостях

Следующий этап — отдельный A/B-эксперимент; здесь он не реализован. Нужно заранее определить период, размер выборки, основную метрику и правила анализа, затем случайно и стабильно распределять гостей между обычным выбором и LinUCB. Группы должны видеть одинаковые блюда и наборы текстов; версии моделей и описаний нужно фиксировать. Логируются назначение группы, фактический показ и реакция, учитывается окно ожидания 30 минут. Для оценки заказов потребуется отдельное событие подтверждённого заказа и правило его связи с показом. Результат оценивается с неопределённостью после завершения заданного периода, без остановки при первом выгодном результате. Текущие наблюдательные счётчики без контрольной группы такой вывод не позволяют.
